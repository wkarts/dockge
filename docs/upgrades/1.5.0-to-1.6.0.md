# Upgrade Dockge 1.5.0 → 1.6.0

Este procedimento considera uma instalação do `wkarts/dockge` usando o `compose.yaml` canônico, com dados persistentes e stacks fora da imagem do container.

## O que é preservado

A atualização do container Dockge não deve remover:

- stacks existentes em `DOCKGE_STACKS_PATH` (padrão `/opt/stacks`);
- arquivos `compose.yaml` e `.env` das stacks;
- containers, redes e volumes pertencentes às stacks já em execução;
- dados do Dockge em `DOCKGE_DATA_PATH`;
- tokens da Automation API em `/app/data/api-tokens.json`;
- auditoria em `/app/data/api-audit.jsonl`.

O `1.6.0` acrescenta persistência explícita para:

```text
/app/data/api-idempotency.json
```

Como `/app/data` já é persistente, o arquivo novo passa a sobreviver às recriações do container Dockge.

## Importante

O Dockge é o plano de gerenciamento das stacks. Recriar apenas o container `dockge` não executa `down`, `up`, `restart` ou `pull` automaticamente nas stacks administradas.

Não use durante o upgrade:

```bash
docker compose down -v
docker system prune -a --volumes
rm -rf /opt/dockge/data
rm -rf /opt/stacks
```

## 1. Conferir caminhos atuais

No diretório onde está o compose do Dockge:

```bash
cd /opt/dockge

docker compose config
```

Confirme principalmente:

```text
DOCKGE_DATA_PATH
DOCKGE_STACKS_PATH
DOCKGE_PORT
DOCKGE_BIND_HOST
```

## 2. Backup recomendado

O backup é preventivo; a atualização normal não apaga esses dados.

```bash
cd /opt/dockge
mkdir -p backup-1.5.0

cp -a compose.yaml backup-1.5.0/
[ -f .env ] && cp -a .env backup-1.5.0/
cp -a data backup-1.5.0/data

sudo tar -C /opt -czf backup-1.5.0/stacks.tar.gz stacks
```

Para instalações com caminhos personalizados, use os valores reais de `DOCKGE_DATA_PATH` e `DOCKGE_STACKS_PATH`.

## 3. Atualizar o compose canônico

Preserve primeiro seu arquivo atual:

```bash
cd /opt/dockge
cp -a compose.yaml compose.yaml.1.5.0
```

Baixe o compose da release estável:

```bash
curl -fsSL https://raw.githubusercontent.com/wkarts/dockge/v1.6.0/compose.yaml -o compose.yaml
```

Se você mantém customizações locais, compare antes de subir:

```bash
diff -u compose.yaml.1.5.0 compose.yaml || true
```

A configuração nova relevante é:

```yaml
DOCKGE_API_IDEMPOTENCY_FILE: ${DOCKGE_API_IDEMPOTENCY_FILE:-/app/data/api-idempotency.json}
```

## 4. Fixar produção em 1.6.0

No `.env` do Dockge, prefira produção pinada:

```dotenv
DOCKGE_IMAGE=ghcr.io/wkarts/dockge
DOCKGE_IMAGE_TAG=1.6.0
DOCKGE_DATA_PATH=./data
DOCKGE_STACKS_PATH=/opt/stacks
DOCKGE_API_TOKENS_FILE=/app/data/api-tokens.json
DOCKGE_API_AUDIT_FILE=/app/data/api-audit.jsonl
DOCKGE_API_IDEMPOTENCY_FILE=/app/data/api-idempotency.json
```

Preserve seus valores atuais de bind, porta, caminhos e opções de segurança quando forem diferentes dos padrões.

## 5. Validar antes da troca

```bash
cd /opt/dockge

docker compose config >/tmp/dockge-1.6.0.compose.validated.yaml
```

Se o comando terminar sem erro, faça o pull:

```bash
docker compose pull dockge
```

## 6. Atualizar somente o Dockge

```bash
docker compose up -d --no-deps dockge
```

Esse comando substitui o container do Dockge pela imagem `1.6.0` sem executar operações nas stacks administradas.

## 7. Verificações pós-upgrade

```bash
docker compose ps

docker compose logs --tail=200 dockge
```

Confirme a aplicação e o volume de dados:

```bash
docker inspect "$(docker compose ps -q dockge)" --format '{{json .Mounts}}'
```

Confirme também que as stacks continuam em execução:

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'
```

O upgrade do Dockge não deve provocar reinício dos containers dessas stacks.

## 8. Rollback para 1.5.0

Se for necessário voltar, não restaure stacks nem apague dados. Troque somente a imagem do Dockge.

No `.env`:

```dotenv
DOCKGE_IMAGE_TAG=1.5.0
```

Depois:

```bash
cd /opt/dockge
docker compose pull dockge
docker compose up -d --no-deps dockge
```

Se o compose antigo tiver customizações que precisam ser restauradas:

```bash
cp -a compose.yaml.1.5.0 compose.yaml
docker compose up -d --no-deps dockge
```

O arquivo `api-idempotency.json` criado pelo `1.6.0` pode permanecer no volume; ele não interfere no retorno da imagem anterior.

## Resumo operacional

```text
Stacks/serviços existentes  → permanecem rodando
/opt/stacks                  → preservado
/app/data                    → preservado
Dockge container             → recriado
Imagem Dockge                → 1.5.0 → 1.6.0
API tokens/auditoria         → preservados
api-idempotency.json         → criado/persistido no 1.6.0
Downtime das aplicações      → não esperado
Downtime do painel Dockge     → apenas durante a recriação do container
```
